# LLM依存度最小化・非依存化に向けた戦略とアーキテクチャ設計

本ドキュメントは、Kami Excel Extractor（神エクセル構造化・RAG最適化エンジン）におけるLLM（大規模言語モデル）への依存を最小限に抑える、あるいは完全にLLMをバイパスして決定論的（ルールベース・ヒューリスティック）に複雑なExcelシートを構造化データへ変換するための詳細な検討とアーキテクチャ設計をまとめたものです。

---

## 1. 背景と目的 (Introduction & Objectives)

現在のデータ抽出システムは、レイアウトが複雑な「神エクセル」を処理するためにマルチモーダルLLM（Gemini、GPT-4o等）をオーケストレーターとして使用しています。しかし、LLMへの全面的な依存には以下のトレードオフが存在します。

1. **コスト（API Cost）**: 巨大なシートや大量のExcelファイルを処理する際、数百万トークンにおよぶコンテキスト消費によりAPIコストが累積する。
2. **レイテンシ（Latency）**: LLMの推論には1シートあたり数秒〜数十秒を要し、リアルタイム処理やバッチ処理のボトルネックとなる。
3. **セキュリティとプライバシー（Security & Privacy）**: 機密性の高いデータ（顧客情報や企業財務など）を外部のパブリッククラウドAPIへ送信することへの懸念。
4. **決定論的再現性の欠如（Lack of Determinism）**: LLMの出力は確率的であり、稀にフォーマットエラーやハルシネーション（存在しないデータの生成）を起こす。

本設計は、これらの課題を根本的に解決するため、**「可能な限りLLMに依存しない（LLM-free）構成」**および**「LLMの利用を最小限に留める（LLM-minimization）ハイブリッド構成」**を可能にする具体的な方法論、アルゴリズム、およびアーキテクチャを提示します。

---

## 2. LLM非依存（LLM-free）を実現する決定論的解析アルゴリズム

神エクセルが「複雑」に見えるのは、結合セル（Merged Cells）や独自の装飾（罫線、背景色）を用いて人間向けにレイアウトされているためです。しかし、これらの視覚情報は、`openpyxl`等のパーサーを介して**CSSスタイルや境界条件の集合として100%デジタルに抽出可能**です。
これらを機械的に解析する「ヒューリスティック（ルールベース）解析エンジン」のコア・アルゴリズムは以下の要素で構成されます。

```
+-------------------------------------------------------------+
|                      Excel ワークシート                     |
+-------------------------------------------------------------+
                               |
                               v
+-------------------------------------------------------------+
|             1. 領域分割 (Region Segmentation)               |
|      - 空白行・列、太い外枠罫線に基づきシートをブロック化   |
+-------------------------------------------------------------+
                               |
            +------------------+------------------+
            |                                     |
            v                                     v
+-----------------------+             +-----------------------+
|  [ケースA] 表形式型   |             |  [ケースB] 帳票・KV型  |
+-----------------------+             +-----------------------+
| 2. 結合ヘッダーの伝播 |             | 2. 視覚的近接度マッピング|
| 3. 行パターンの連続性 |             | 3. 2カラム構造の検出  |
+-----------------------+             +-----------------------+
            |                                     |
            +------------------+------------------+
                               |
                               v
+-------------------------------------------------------------+
|                     構造化データ (JSON)                      |
+-------------------------------------------------------------+
```

### 2.1 領域分割 (Region Segmentation)
1シート内に複数の表や帳票（メタデータフォーム＋データテーブル）が同居している場合、シート全体を一括で表変換すると構造が崩れます。
- **空白行・列によるセグメンテーション**: 1行または1列が完全に空白（または特定文字のみ）である境界線を検知し、シートを自律的なサブグリッド（セクション）に分割します。
- **罫線による境界検知 (Border-based Boundary)**: 太線（`thick` / `medium`）で囲まれた領域、または二重線（`double`）で区切られた領域を、論理的な表の境界として識別します。

### 2.2 表形式（Table-style）と帳票形式（Form/KV-style）の自動識別
分割された各領域について、それが「リスト形式のテーブル」であるか「キー・バリュー形式の帳票」であるかを自動判別します。
- **テーブル判別指標**:
  - 特定の行（通常は先頭行）のセルが太字（Bold）または背景色ありであり、それ以降の複数行が同じ列構成かつ同様のデータ型（文字列、数値、日付など）を繰り返している場合、**「表（Table）構造」**と判定。
- **帳票（Key-Value）判別指標**:
  - セル結合が不規則で、隣接するセル同士に「背景色あり（ラベル）」と「背景色なし（値）」のペアが格子状または水平・垂直に並んでいる場合、**「キー・バリュー形式（Form）」**と判定。

### 2.3 結合セルの論理復元とヘッダー伝播
神エクセル最大の難所である結合ヘッダーについて、決定論的に値を補正します。
- **多段結合ヘッダーの補間**: `A1:C1` が「基本情報」として結合され、2行目の `A2` が「氏名」、`B2` が「年齢」、`C2` が「性別」となっている場合、結合セルの左上セルの値（「基本情報」）をスパン内のすべての列に伝播させ、下層のキーと結合（例：`{"基本情報_氏名": "...", "基本情報_年齢": "..."}`）します。

### 2.4 キー・バリュー形式の視覚的近接度マッピング（Proximity Mapping）
帳票（KV）形式のブロックでは、以下のヒューリスティックに基づいてキーと値をマッピングします。
- **右方向（Horizontal Link）**: セル `(r, c)` がラベル（太字、背景色あり、または末尾がコロン「：」）で、右隣のセル `(r, c+1)` または結合された右領域が値。
- **下方向（Vertical Link）**: セル `(r, c)` がラベルで、直下のセル `(r+1, c)` またはその結合領域が値。

## 3. LLM利用の最小限化（LLM-minimization）ハイブリッド構成

完全にLLMを排除するのではなく、**重い処理やレイアウト認識はヒューリスティックで行い、LLMは解釈やクレンジングといった「言語的タスク」にのみピンポイントで利用する**設計です。これにより、消費トークン数とAPI呼び出し回数を劇的に削減（最大90%削減）します。

### 3.1 ハイブリッドアーキテクチャの構成
```
+-------------------------------------------------------------+
|                      Excel ワークシート                     |
+-------------------------------------------------------------+
                               | (Deterministic)
                               v
+-------------------------------------------------------------+
|             決定論的パーサー (Heuristic Parser)              |
|          - 領域抽出、セル配置の正規化、HTML/JSON化          |
+-------------------------------------------------------------+
                               | 構造化された粗データ (Raw JSON)
                               v
+-------------------------------------------------------------+
|                 LLM最小限クレンジングレイヤー                |
|      - [言語タスク1] 曖昧なキー名の名寄せ (Schema Mapping)   |
|      - [言語タスク2] 住所・氏名等の表記揺れ正規化            |
|      - [言語タスク3] VLMによる画像内テキストのメタ抽出       |
+-------------------------------------------------------------+
                               | (Low Token Context)
                               v
+-------------------------------------------------------------+
|                     最終構造化 JSON / MD                     |
+-------------------------------------------------------------+
```

### 3.2 最小限化へのアプローチ

| 処理フェーズ | 従来のLLM全面依存アプローチ | ハイブリッド（LLM最小限）アプローチ | 削減効果 |
| :--- | :--- | :--- | :--- |
| **表構造の把握** | HTML全体と画像(VLM)をプロンプトに積み、LLMに表を復元させる。 | 決定論的パーサーが結合セルや罫線から正確なテーブル構造（配列・辞書）を事前に構築。 | **トークン量：80〜90%削減**<br>フォーマットエラーの発生率を0%に。 |
| **画像・グラフ解析** | シート内の全画像をVLMに渡し、詳細な要約を生成。 | 1. 決定論的に画像が「単なる装飾（会社のロゴ等）」か「データ画像」かをファイルサイズやアスペクト比で分類。<br>2. 必要なグラフ画像のみを軽量ローカルVLMに投げる。 | **VLM呼び出し回数：50%以上削減** |
| **スキーママッピング** | LLMが直接Pydanticスキーマに合わせてデータを生成。 | 1. 決定論的パース結果から「キー」の一覧のみをLLMに渡す。<br>2. LLMは事前に定義された目標スキーマと、抽出されたキーの対応関係（マッピング辞書）のみを生成。<br>3. プログラム側でマッピング辞書を適用。 | **LLMコスト・実行時間：95%削減**<br>（データ本体ではなく、キーの対応関係のみを判定するため超高速） |

## 4. エッジ環境での完全ローカル実行（Local LLM Integration）

APIコストやデータ送信のセキュリティ懸念をゼロにするため、本システムは **Ollama** を用いた完全ローカル実行に対応しています。

### 4.1 推奨されるローカル動作構成
- **CPU/GPU**: Apple Silicon (M1/M2/M3) または NVIDIA GPU (VRAM 8GB以上推奨)
- **テキスト・構造化抽出**: `qwen2.5-coder:1.5b` または `qwen3.5:4b`
  - *理由*: Qwen-Coderシリーズは、JSON構造の生成や表形式データの指示追従能力が極めて高く、軽量（1.5B〜4B）ながら商用モデルに匹敵する精度を発揮します。
- **画像（Vision）解析**: `moondream` (極めて軽量なVisionモデル)
  - *理由*: グラフや図表の概要を数秒でローカル処理可能。

### 4.2 ハイブリッドローカル構成 (Heuristic + Local LLM)
ヒューリスティックパーサーでExcelをパースした後、ローカル起動している `qwen2.5-coder:1.5b` に対し、
「この表のキー名を標準の項目名にマッピングしてください」といった短いプロンプト（消費トークン数 < 300）を投げることで、エッジ環境でもほぼノーコスト・ミリ秒単位で高精度なデータ抽出を完結できます。

## 5. 各構成の比較評価 (Architectural Trade-offs)

| 評価項目 | ① 従来型（LLM全面依存） | ② ハイブリッド（ヒューリスティック＋LLM） | ③ 完全非依存（ヒューリスティックのみ） |
| :--- | :---: | :---: | :---: |
| **複雑なレイアウト対応力** | 🟢 非常に高い (意味的に推論) | 🟢 非常に高い (構造化後に意味補正) | 🟡 中程度 (パターン外の変則表で低下) |
| **データの正確性・再現性** | 🟡 確率的 (ハルシネーションあり) | 🟢 非常に高い (数値は決定論的) | 🟢 100% 決定論的 (正確無比) |
| **APIコスト** | 🔴 高い (トークン従量) | 🟢 極めて低い (マッピング時のみ) | 🟢 **0円** (完全無料) |
| **処理速度（レイテンシ）** | 🔴 遅い (1シートあたり 5〜15s) | 🟡 中速 (1〜3s) | 🟢 **超高速** (50〜200ms) |
| **データセキュリティ** | 🟡 クラウドへのデータ送信が必要 | 🟢 エッジローカルモデルで完結可能 | 🟢 **完全安全** (外部送信一切なし) |
| **開発・保守コスト** | 🟢 プロンプト調整のみで簡単 | 🟡 ヒューリスティックと併用で中程度 | 🔴 特殊レイアウト用ルール追加が必要 |

## 6. 実装設計：決定論的ヒューリスティックパーサー (HeuristicExcelParser)

本プロジェクトにおいて実用性を証明するため、複雑な結合セルや帳票をパースできる具体的な `HeuristicExcelParser` クラスを `src/kami_excel_extractor/heuristic_parser.py` に実装します。

### 6.1 コア機能仕様
1. **`HeuristicExcelParser`**:
   - `openpyxl` のワークシートを直接処理する。
   - シート内の結合セル（`ws.merged_cells.ranges`）をスキャンし、すべてのキー／値セルのスパン情報（rowspan, colspan）をインデックス化。
   - 結合されたヘッダーや空白をインテリジェントに埋め、データ構造をフラットまたはネストした辞書/リストに復元。
2. **多重テーブル対応**:
   - 行が空いている（値がすべて None）ことをシグナルとして、複数の小さなサブテーブルに分割処理。
3. **キー・バリュー抽出モード**:
   - 表形式ではなく、申請書や報告書などの「一対一のラベル対」を抽出するロジック。
   - ラベルを太字、背景色、またはセルの位置関係（左から右、上から下）から自動検知。

## 7. 今後のロードマップと導入手順

### フェーズ 1: ヒューリスティックコアの導入 (現在進行)
- 100% LLMフリーで動作する `HeuristicExcelParser` の実装。
- LLMを使用しない `--model heuristic` オプションを CLI および API に追加。
- 包括的なユニットテストを作成し、既存のテストスイート（`pytest`）と並行して完全な再現性を維持することを確認。

### フェーズ 2: 選択的LLMハイブリッド（プログレッシブ抽出）
- ヒューリスティック解析により「構造化が部分的に失敗した（またはデータ信頼性が低い）」と判定されたエリアのみを切り出し、局所的にLLM（またはローカルLLM）に投げて構造を洗練させる「2フェーズ抽出パイプライン」の開発。

### フェーズ 3: 自動レイアウト分類モデルの搭載
- Excelの各シートが「Simple Table」「Complex Table」「Key-Value Form」「Dashboard/Mix」のどれに該当するかを、高速な機械学習モデル（ランダムフォレストや軽量なローカル分類器）で自動判定し、最適なパースパイプライン（ヒューリスティック or LLM）へ動的にルーティングする自律型エンジンの構築。
